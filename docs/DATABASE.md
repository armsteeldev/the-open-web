# Database

The platform uses one SQLite database in WAL mode with a 5-second busy timeout. Node.js 22's built-in `node:sqlite` API provides one shared connection in the single Fastify process. No database server or cache is involved.

## Ownership and data access

Each space owns its tables, constraints, indexes, transactions, and query functions. Keep them beside its backend module, for example `apps/server/src/spaces/wall/database.ts`. Prefix new table and index names with the stable space ID to make ownership clear. Do not import another space's data-access code or query its tables. The database connection is shared, so ownership is an application convention rather than SQLite-enforced per-module permissions.

The existing Wall tables are `wall_tiles` and `visitor_cooldowns`. They keep their released names and format for compatibility. `wall_tiles` stores a 10,000-byte row-major palette-index blob for each touched 100 × 100 tile, keyed by tile coordinates. The Wall validates tile size and palette indices before reading or writing. `visitor_cooldowns` stores a SHA-256 digest and last placement time. Migration 002 indexes its timestamps so expired digests can be purged in batches. Neither table stores network addresses.

The Wall wraps expiry cleanup, cooldown check, tile overwrite, and cooldown update in `BEGIN IMMEDIATE`; failures roll back. Its behavior remains an overwrite, with the latest committed pixel and event order aligned. There is no automatic Wall reset.

## Migrations

Migration 003 creates three Global Chat-owned tables. `chat_messages` stores the autoincrement ID, server timestamp, shared visitor digest, nickname and plain text, with indexes for recent history and repeated-text checks. `chat_idempotency` stores a visitor digest, UUID request key, accepted message ID and timestamp; entries expire after one hour and are capped at 10,000. Its visitor/time index also backs the three-second cooldown when a message row is removed. `chat_message_removals` holds bounded ID/time tombstones so the running process can publish removals made by retention, the hard count cap, or the operator command. Message text is limited to 360 UTF-8 bytes and nickname to 24 Unicode code points/48 UTF-8 bytes. Messages expire after 24 hours and the table is capped at 2,000 rows. No IP address is stored.

Migration 004 creates three Message in a Bottle-owned tables. `bottle_messages` stores a server UUID, UTC Unix-millisecond time, plain text of at most 500 UTF-8 bytes, and an optional 24-code-point/48-byte self-declared signature; the table is capped at 10,000 rows by pruning the oldest records transactionally on release. `bottle_visitor_cooldowns` stores only visitor digest and last release time for the 20-second cooldown, expires after the cooldown, and is capped at 10,000 rows. `bottle_idempotency` stores the digest, UUID request key, accepted bottle ID, and time for safe retries; entries expire after 24 hours and are capped at 10,000. No IP address is stored. Bottle does not query Wall or Chat tables.

Migration 005 creates independent tables for the four Expansion Phase I spaces. Guestbook stores up to 25,000 entries for five years, with a 24-code-point/48-byte optional display name and a 220-code-point/500-byte message. Its visitor cooldown and retry-key tables store only the shared digest, timestamps, and payload hash; the retry table cascades when an entry is removed. The Story stores up to 100 chapters with 40 ordered passages each. A removed passage becomes a tombstone in place; it is not deleted. Chapter revision and current-chapter constraints serialize concurrent continuations. Open Questions stores up to 5,000 questions for three years and up to 100 answers per question/20,000 total. Question rows retain no asker identity; answer rows keep the digest needed for one current answer per cookie. Question removal cascades to answers and both retry tables. The Choice stores one active/queued/closed decision sequence, at most 20 queued proposals, at most 10,000 active votes, and an archive of 100 completed decisions. It stores only aggregate results after close and deletes individual vote rows then. All four table groups are `STRICT`, use space-prefixed names, bounded text checks, and explicit indexes for reads and cleanup.

The 005 bridge fingerprint is calculated over all four new `sqlite_schema` object groups. A release can roll back only to a runner that recognizes this exact fingerprint. The dedicated [rollback compatibility sequence](ROLLBACK-COMPATIBILITY.md) deploys that forward-compatible bridge before 005 is applied. The bridge does not contain migration 005 and does not register the four new spaces; it accepts only the exact known 005 schema if a feature-release rollback is needed. Unknown migration versions and altered schemas still fail closed.

Migration 006 creates only Drawing Board (`draw_*`), Garden (`garden_*`), and Visitors Map (`map_*`) tables and indexes. Drawings contain a server ID, creation time, and validated vector strokes; visitor identity is kept only in the short-lived submission cooldown table, never on a drawing. Garden plants contain position, species, and creation time; private identity is kept only in its planting cooldown table. Map contributions retain one private cookie digest and current ISO alpha-2 country code per browser so that mark can be changed or removed. The map API returns country aggregates and the requesting browser's own country only. Each table group is `STRICT`, bounded, and indexed for its read or cleanup path.

The 006 compatibility fingerprint is `718a3c10db4694071153003263cd695a6d322b6bf5bbce45d8bc379dabb8a046`. The final-expansion bridge validates exact migrations 004, 005, and 006 but contains migrations only through 004 and does not register the final spaces. Migration 006 applies transactionally only in the ten-space candidate after the bridge has become the verified rollback target. The complete transition and failure simulation are documented in [ROLLBACK-COMPATIBILITY.md](ROLLBACK-COMPATIBILITY.md).

Files in `database/migrations` use consecutive three-digit numbers and an owner/purpose suffix. Migration 006 is the final planned spaces migration. The runner applies each migration and its version record in one transaction. Gaps, duplicate numbering, failed SQL, newer database history, and inconsistent histories fail closed. A failed migration rolls back its schema changes. There is no automatic reverse migration.

Once released, a migration file is immutable. Make the next schema change in a new numbered file. Keep a migration narrow and compatible with the previously deployed application: code rollback does not automatically roll back a database. Do not add tables for spaces that have not been built. Test new migrations on a disposable database and verify that existing Wall rows and tables remain intact.

## Backup and restore

Before production schema changes, follow [BACKUPS.md](BACKUPS.md). `scripts/backup.mjs` uses SQLite's online backup API, verifies integrity including committed WAL content, writes with private permissions, publishes atomically, and refuses to overwrite an existing backup. Production activation requires a fresh verified backup on the approved separate HDD before switching releases.

Test restores on disposable copies. Never replace an active WAL database beneath the running service. For actual recovery, preserve the current database plus WAL/SHM files, use a verified backup, stop only the Open Web service, and follow the documented recovery checks. Restoring an older backup discards writes after its snapshot.
