# Global Chat

Global Chat is one permanent public text room at `/chat`. Visitors can read recent messages and send text immediately with the shared anonymous cookie. Each visitor sees a stable, server-derived nine-digit anonymous label while their cookie remains. An optional nickname appears alongside that number, so repeated nicknames remain distinguishable. Nicknames do not create accounts or grant exclusive rights. The generated `Anonymous` plus digits pattern is reserved. There are no channels, direct messages, profiles, attachments, edits, reactions, or message formatting.

The interface is a chronological plain-text list with compact sender rows, local 24-hour timestamps, an optional locally remembered nickname, connection state, and a one-line composer. Timestamps keep UTC epoch milliseconds on the server; the browser displays local time and adds a local date when a message is from another day. Text and nickname values are rendered with DOM text nodes. Incoming messages do not trigger screen-reader announcements. When a visitor scrolls up, new lines do not move the reading position; a small button returns to the newest messages. Drafts stay in the input through network and reconnect failures. The nickname editor is a keyboard-accessible dialog; changing a nickname affects future messages only.

## HTTP API

All routes are same-origin and under `/api/chat/`.

### `GET /api/chat/history`

Returns the latest 100 messages from the last 24 hours, ordered by server-assigned ID:

```json
{
  "messages": [
    { "id": 17, "createdAt": 1794327000000, "nickname": "Anonymous", "anonymousId": "482901735", "text": "Hello" }
  ],
  "latestId": 17,
  "oldestId": 17,
  "identity": { "anonymousId": "104527893" }
}
```

`oldestId` is `null` for an empty snapshot. `latestId` is `0` when no unexpired messages remain. The additive `identity` field describes the current visitor; each message's `anonymousId` is derived from the digest already stored with that message, including messages created before this interface update. This read also issues the existing `ow_id` cookie when a visitor does not already have one; it does not create a visitor row. Responses are `Cache-Control: no-store`.

### `POST /api/chat/messages`

Requires the shared anonymous session, exact allowed `Origin`, and enabled write gate. Example request:

```json
{
  "requestId": "d7e2cc8a-4b46-4a47-8a48-fbd24194a23a",
  "nickname": "Mira",
  "text": "Hello from Stockholm"
}
```

`requestId` must be a UUID v4 generated by the browser. It is scoped to the shared cookie digest and makes short-lived retries idempotent. The server assigns `id`, `createdAt`, and `anonymousId`; client-supplied trusted fields are ignored. Success returns `{ "ok": true, "duplicate": false, "message": ... }`. A retry returns the original message with `duplicate:true`; if it has since been removed or expired, the server acknowledges the accepted retry with `message:null` and does not recreate it.

Invalid or empty content returns `400`. A missing shared session returns `401`. Origin rejection is `403`. Cooldowns and abuse limits return `429` with an `error` category and `retryAfterMs`. The emergency write gate returns `503`. The server's 1 KiB request bound remains in place.

Messages are normalized to NFC, have line breaks and repeated whitespace collapsed, and are limited to 360 UTF-8 bytes. Whitespace-only text and unsafe control or bidirectional override characters are rejected; international text, emoji, and emoji joiners are accepted. Nicknames are trimmed, whitespace-collapsed, limited to 24 Unicode code points and 48 UTF-8 bytes; an absent or blank nickname displays as `Anonymous` with the visitor's number. A custom nickname appears with a formatted `#number` and is remembered only in that browser's local storage. A nickname change affects future messages; stored rows are not rewritten. Nicknames may be reused by anyone. The generated `Anonymous` followed by digits is reserved to reduce obvious impersonation. HTML-looking text remains literal.

## Realtime and recovery

The browser subscribes only to `/api/events?space=chat`, then requests history. It buffers events while the history request is in progress, merges by server ID, applies removal events, and displays the latest 100 in ID order. The snapshot and high-water ID are read in one SQLite transaction. This subscribe-before-snapshot flow covers messages created while history is loading without requiring durable WebSocket replay.

On socket loss, the browser preserves the input and visible messages, reconnects with exponential backoff and jitter up to 30 seconds, and fetches a fresh snapshot before reporting Connected. This recovers writes sent during the outage, duplicate delivery, and data changes after a server restart. If a history fetch fails, the browser keeps buffering live events and retries with exponential backoff and jitter up to 30 seconds, avoiding a rapid retry storm while the API is recovering. Its event buffer is capped; overflow triggers another full snapshot. No old-space events can reach the `chat` subscriber.

Message events are `{v:1,space:"chat",type:"message",id,createdAt,nickname,anonymousId,text}`. The identifier is an additive field in protocol version 1; older readers can ignore it. Removal events are `{v:1,space:"chat",type:"remove",id}`. Server commit happens before publish. HTTP confirmation and live echo may race; the browser deduplicates both by message ID. Removal tombstones are published during the next maintenance pass, no later than about 30 seconds after an operator command in a healthy process.

## Identity, stored data and retention

Chat uses the platform's single HttpOnly `ow_id` cookie. It does not add accounts or expose cookie values or digests. A message row stores its server ID/time, display nickname, plain text, and the shared cookie digest needed for the per-visitor cooldown. The server hashes that existing digest with a chat-specific domain separator and reduces it to a nine-digit decimal label. Only that label leaves the server; the raw cookie and internal digest are not included in history, HTTP send results, or events. No extra visitor table or personal data is stored. Clearing the cookie creates a new random identity, which can coincidentally map to the same short label.

The nine-digit label is recognizable but not guaranteed unique or verified. For 2,000 distinct retained visitor identities, the approximate probability of at least one label collision is 0.2%; larger visitor populations raise that probability. When two visitors collide, their displayed labels may match. This is a short public distinction aid, not proof of one human or an account ID. Existing messages already retain their visitor digest, so the server derives their labels without rewriting rows or inventing associations. Older API readers can ignore the additive `anonymousId` fields.

Network addresses are used only by bounded in-memory platform and Chat limiters; they are not persisted. Server request logging is disabled and message bodies are not logged.

Migration 003 adds:

- `chat_messages`: at most 2,000 rows, deleted after 24 hours, with indexes for ID order and repeat checks.
- `chat_idempotency`: request UUID and visitor digest for at most one hour, capped at 10,000 rows. It contains no message text, backs the visitor cooldown, and remains after message deletion so a retry cannot recreate removed content.
- `chat_message_removals`: message ID and removal timestamp only, retained up to 24 hours and capped at 5,000 rows for in-process removal delivery.

The service removes up to 100 expired messages per 30-second maintenance pass, even when the room is idle; a separate bounded pass repairs any excess over the hard cap. New writes enforce the 2,000-row cap transactionally. New visitors see up to 100 messages; there is no older-message archive API. SQLite WAL and existing release backups cover Chat data. Code rollback leaves the additive migration in place.

## Abuse limits

In addition to the shared 600 requests/minute and 180 POST requests/minute per-network guards and the shared 500 WebSocket / 10 per-network connection caps, Chat uses:

- one accepted message every three seconds for a shared anonymous cookie digest, enforced transactionally in SQLite;
- a per-network token bucket with 20 burst tokens and one token refilled every three seconds;
- a process-wide token bucket with 120 burst tokens and a five-message-per-second refill;
- a same-cookie, same-text repeat check for 30 seconds.

Only accepted messages consume Chat token-bucket capacity. Validation, visitor cooldown, duplicate retries and repeat rejections refund any provisional tokens. In-memory network and global buckets reset on restart. These controls slow basic floods and cookie rotation, but do not identify a person or prevent distributed abuse. Chat's writes use the shared origin check and emergency write gate.

## Operator removal

There is no public admin route or dashboard. An operator with access to the production database can remove one message by its public numeric ID. Inspect the ID in the recent-history API, then run the compiled command as the service account with the exact database path configured for the service:

```sh
sudo -u open-web env DB_PATH=/var/lib/the-open-web/open-web.sqlite \
  node /opt/the-open-web/current/dist/apps/server/src/spaces/chat/remove-message.js 123
```

Replace the database path with the active `DB_PATH` from the service environment and `123` with the target message ID. The command checks that the Chat schema exists, uses a bounded SQLite transaction, removes the row, and writes an ID-only tombstone. Connected browsers receive a `remove` event on maintenance; reconnecting browsers receive a fresh history without the message. A short idempotency record remains so retries cannot restore removed content. The command does not log text. Do not edit the database manually.

For a complete write stop, use the shared `WRITE_GATE_PATH` or `WRITES_ENABLED=false`; that stops writes across both spaces. Keep the existing release backup and rollback procedure in [DEPLOYMENT.md](DEPLOYMENT.md).

## Tests and maintenance

`tests/chat.test.ts` covers validation, UTF-8 bounds, stable and colliding public labels, cookie clearing, duplicate nicknames, origins, ordering, concurrency, duplicates, retention, caps, removals, and persisted identity. `tests/chat-presentation.test.ts` covers visitor-local time and local-midnight dates. `tests/chat-recovery.browser.mjs` verifies increasing history retry delays, buffering of a live event during an API outage, and recovery from a fresh snapshot. `tests/chat.browser.mjs` covers empty and populated layouts, nickname editing, plain-text rendering, local timestamps, pending/error/cooldown states, snapshot/live races, scroll preservation, reconnect recovery, keyboard sending, narrow screens, and landscape. `tests/accessibility.browser.mjs` runs axe checks on desktop and mobile in empty, populated, dialog, and open-navigation states. `npm run test:load` retains the 500-client Wall scenarios and runs 400 Wall plus 100 Chat clients together, checking same-space delivery and cross-space isolation. All these checks use disposable local databases; never direct them at the public service.
